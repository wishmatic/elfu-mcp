# Inline URL sources

Status: Done
Depends on: none
Supersedes: `docs/plans/done/FILES_AND_LATEST_PLAN.md` and the abandoned LibreChat API design it was replaced by

## Goal

Make `inline` work on the two kinds of URL an agent actually receives in this deployment, and make this MCP a
one-tool server again.

The workflow that motivates it: the user pastes an image into LibreChat, the agent asks the user for the image's URL
(see `docs/PROMPT.md`), and the user pastes the URL that LibreChat shows. That is a LibreChat URL, and this service
cannot fetch it: `/images/*` needs a `refreshToken` cookie, `/api/files/download/...` needs a bearer token. The MCP
server runs next to LibreChat with its data directory mounted, so it can read the file from disk instead.

The second kind is a URL this service already produces elsewhere: an image generated by `neo-mcp` sits at `neo-mcp`'s
`PUBLIC_HOST`, which the MCP server cannot reach by name from inside the network. It can reach `neo-mcp` under a
different, private base URL, so the public prefix has to be rewritten.

Both are the same problem, so both are solved by one configuration: a map from a public URL prefix to the place this
service can actually read it from, either a directory on disk or a reachable base URL.

## Non-goals

- Reading LibreChat's API, minting tokens, or holding `JWT_SECRET`. None of that is needed when the data directory is
  mounted, which is why this plan replaces the API-based design.
- `files` and `latest`. Dropped, along with the in-memory registry, the LibreChat client, and the digest-keyed state
  they needed. This MCP has one tool.
- Writing, uploading, or modifying anything. Every read is read-only.
- Serving files. Nothing stores an image, so nothing needs to serve one. Whether the existing file store and `/i/*`
  surface should now be removed is an open question below.
- Probing, following, or discovering hosts. Only configured prefixes are rewritten; everything else is fetched exactly
  as it is today.

## Design

### One envar

```sh
INLINE_URL_MAP=https://chat.example.com/images/=http://librechat:3080/images/,https://neo.example.com=http://neo-mcp:8080
```

Comma-separated `public=private` pairs. Whitespace around entries is trimmed. The split is on the first `=`, so a URL
containing one is fine on either side.

- A key is a public URL prefix: an absolute `http`/`https` base, optionally with a path. A key with a query or fragment
  is rejected, and keys must be unique.
- A value is either an absolute `http`/`https` base URL, or a filesystem directory.

The container needs a `LIBRECHAT_`-free name because the map is not LibreChat-specific: `neo-mcp` entries use it too,
and any future source would.

### Matching

A URL matches an entry when its scheme and host are equal, case-insensitively, and its path starts with the entry's
path. The longest matching path wins, so a specific prefix can override a host-wide one. The remainder of the path is
appended to the private side: the rest of the path for an HTTP entry, and the rest of the path under the directory for
a disk entry.

Matching happens per hop inside `resolve.Resolver.Fetch`, next to the existing check that maps this service's own
`PUBLIC_HOST` to the file store, so a redirect into a mapped prefix is rewritten too.

### Reading from disk

The remainder of the path is URL-decoded, cleaned, and joined under the mapped directory. The read is refused when the
remainder is empty, absolute, or contains a `..` segment; when the joined path escapes the directory, checked the same
way the file store checks its keys; when the extension is not one this service decodes; or when the file is larger than
the read cap. Anything refused is an error, the same way a failed fetch is, so the tool reports it.

The whitelist and the escape check are what keep a mapped directory from becoming arbitrary local file read.

### The secret that is not a secret

A disk entry hands this service the ability to read a directory, and nothing authenticates the caller beyond the URL
they supply. The operator's protection is that the key is long and unguessable, so knowing the prefix is the
authorization, exactly as the user asked for. Two consequences to be explicit about:

- `inline` logs the URL it was asked for, as upstream does. A key that is secret therefore appears in this service's
  logs, and in the conversation the URL came from. It is unguessable, not confidential.
- An HTTP entry carries no such property and needs none: it is a routing convenience, not a capability.

The private side of a mapping, whether a directory or an internal base URL, is never logged.

### Configuration

| Envar            | Default | Meaning                                                                     |
| ---------------- | ------- | --------------------------------------------------------------------------- |
| `INLINE_URL_MAP` | empty   | `public=private` pairs as above. Empty means every URL is fetched as today. |

A malformed map is a startup error, not a silent skip, since a typo would otherwise show up as a fetch failure much
later.

## Open question

The file store and its `/i/*` route exist because the bootstrap needed a working file server, and the resolver uses the
store to read this service's own `PUBLIC_HOST` URLs without a network hop. Nothing writes to the store, and
`INLINE_URL_MAP` covers the self-URL read, so the store is now dead weight that also forces `PUBLIC_HOST` and
`FILES_DIR` to be configured. Removing it is a separate, larger change than this plan and needs a decision, so this plan
leaves it alone.

## Implementation units

### Unit 1: the source map

Deliverables: `internal/sourcemap/sourcemap.go`, `internal/sourcemap/sourcemap_test.go`.

Acceptance criteria:

- [x] `Parse("")` yields a map with no entries, and `Lookup` then matches nothing.
- [x] A pair with an empty side, a key that is not an absolute `http`/`https` URL, a key with a query or fragment, or a
      duplicate key is an error naming the offending entry.
- [x] A value starting with `http://` or `https://` is an HTTP entry; anything else is a directory entry.
- [x] The longest matching path wins, so `https://h/a/` beats `https://h/` for `https://h/a/x`.
- [x] Host matching is case-insensitive, and a path match must be a real prefix boundary: `https://h/img` does not match
      `https://h/images/x`.
- [x] The remainder for an HTTP entry is the path after the key, and rewriting produces the value's base plus that
      remainder.
- [x] The remainder for a directory entry is the URL-decoded path after the key.
- [x] `FilePath` refuses an empty, absolute, or `..`-bearing remainder, refuses an extension this service does not
      decode, and refuses a path that would escape the directory.
- [x] `FilePath` accepts a legitimately nested path such as `2026-09/abc.png`.
- [x] `go build ./...`, `go vet ./...`, and `go test ./... -race -count=1` pass, and the package imports no other
      package of this module.

### Unit 2: resolving through the map

## Verification

Per unit, `go build ./...`, `go vet ./...`, and `go test ./... -race -count=1`, plus `go list -deps` for the package
boundaries. The map, the escape checks, and the rewrite are all testable with a temp directory and an `httptest` server,
so the parts that matter are covered without a deployment. The mapping between a real LibreChat image path and the
mounted directory is a deployment fact, which is what the Unit 4 human checks are for.
